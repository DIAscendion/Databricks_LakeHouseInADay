# Databricks Gold Model Physical: Shipment Domain

This document defines the physical data model for the Gold layer of the Databricks Lakehouse, focusing on the SHIPMENT process and related entities. The model is designed for aggregated, dimensional, and fact data, with robust audit and error tracking, using Delta Lake tables compatible with Databricks SQL and PySpark.

---

# Gold Layer DDL Scripts

## 1. GO_SHIPMENT_FACT Table

```sql
CREATE TABLE IF NOT EXISTS gold.go_shipment_fact (
  shipment_fact_id STRING,
  shipment_reference_number STRING,
  shipment_status STRING,
  shipment_type STRING,
  leg_type STRING,
  creation_date DATE,
  creation_source STRING,
  creator_role STRING,
  cancelled_flag BOOLEAN,
  reconciled_flag BOOLEAN,
  trailer_number STRING,
  company_identifier STRING,
  parent_shipment_reference STRING,
  origin_facility_name STRING,
  destination_facility_name STRING,
  route_reference STRING,
  bill_of_lading_number STRING,
  business_partner_identifier STRING,
  mode_of_transport STRING,
  total_route_distance DECIMAL(10,2),
  direct_distance DECIMAL(10,2),
  out_of_route_distance DECIMAL(10,2),
  distance_unit_of_measure STRING,
  number_of_stops INT,
  equipment_type STRING,
  bill_to_postal_code STRING,
  bill_to_state_province STRING,
  billing_method STRING,
  purchase_order_reference STRING,
  reconciliation_date DATE,
  load_date TIMESTAMP,
  update_date TIMESTAMP,
  source_system STRING
)
USING DELTA
PARTITIONED BY (shipment_status, shipment_type);
```

# Data Retention Policies

## Retention Periods for Gold Layer
- **Active Data:** 3 years from load_date
- **Error/Audit Data:** 5 years from load_date

## Archiving Strategies
- Data older than retention period is moved to a separate archival storage (e.g., Azure Data Lake archival zone or S3 Glacier)
- Use Databricks OPTIMIZE and VACUUM commands for Delta tables to manage storage and performance
- Error and audit logs are periodically exported to long-term storage for compliance

# Assumptions and Design Decisions
- All id fields (e.g., *_id) are added as STRING and are expected to be generated as UUIDs or similar.
- No PK/FK/constraints are enforced in DDL (Databricks/SparkSQL limitation).
- Partitioning is chosen on business-relevant columns for performance.
- All tables use Delta Lake format for ACID compliance and time travel.
- Metadata columns (load_date, update_date, source_system) are included in all tables.
- Error and audit tables are included for robust data governance.
- Update DDL script section is provided for future schema changes.
- Data retention and archiving strategies are documented for compliance.
- All columns from Silver layer are included in Gold layer tables as required.
- Data types are chosen for Databricks SparkSQL compatibility.
